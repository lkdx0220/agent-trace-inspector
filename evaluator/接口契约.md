# Evaluator 接口契约（Phase 1）

> 目标：让「题集 / harness+scorers / 被测项目」三层解耦。
> 共享的是 harness + scorers；题集统一 schema 但内容各自维护；被测项目只实现 adapter + 版本戳。

## 一、目录结构

```text
agent-trace-inspector/
  evaluator/
    contract.py            # 本文件对应的数据契约（AgentResult）
    manifest.py            # RunManifest 读写
    lint.py                # 题集体检
    config.example.yaml    # judge 模型/窗口/阈值/并发
    接口契约.md
  evalset/
    schema.json            # 题集 JSON Schema
    <project>/cases.json   # 实际题集（Phase 3 再入库；internal 默认不进公开仓库）
  runs/<run_id>/
    manifest.json
    results/*.json         # 每题一条 AgentResult + 分数
    report.html
```

原则：

1. evaluator 不 `import` 被测项目代码；统一「子进程 + JSON 交换」；
2. 每题必须返回 `status`：`ok / timeout / agent_error / empty`，不允许静默降级；
3. 题集数据、运行结果、诊断产物不进公开 git；schema / 代码 / 配置模板进 git。

## 二、Adapter 契约

被测项目提供一个可执行适配器。推荐协议：

```text
父进程 -> 子进程 stdin:  {"question": "...", "context": "...", "case_id": "R7"}
子进程 -> stdout:        AgentResult JSON
子进程超时 / 非零退出：父进程直接 kill，写 status=timeout / agent_error
```

### AgentResult 字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `schema_version` | string | 是 | 当前 `"1.0"` |
| `adapter` | string | 是 | 适配器名，如 `genshin` |
| `adapter_version` | string | 是 | 适配器协议版本 |
| `agent_version` | string | 是 | 被测项目 commit / KB 版本 |
| `status` | enum | 是 | `ok / timeout / agent_error / empty` |
| `error` | string | 否 | 非 ok 时的原因 |
| `answer` | string | 是 | 最终回答（status=empty 时允许空） |
| `contexts` | string | 是 | 工具返回/检索上下文拼接文本 |
| `tool_trace` | array | 否 | 工具调用列表，每项至少 `{name, args, status, result_preview}` |
| `timings` | object | 是 | `init_seconds / agent_seconds / scoring_seconds` |
| `raw` | object | 否 | 适配器原始返回，供排查 |

示例：

```json
{
  "schema_version": "1.0",
  "adapter": "genshin",
  "adapter_version": "1.0",
  "agent_version": "c01e0a0",
  "status": "ok",
  "error": "",
  "answer": "……",
  "contexts": "……",
  "tool_trace": [
    {"name": "hybrid_search", "args": {"query": "……"}, "status": "success", "result_preview": "……"}
  ],
  "timings": {"init_seconds": 51.7, "agent_seconds": 5.0, "scoring_seconds": 0.0},
  "raw": {}
}
```

## 三、Run Manifest

每次跑测落盘 `runs/<run_id>/manifest.json`，字段固定：

```json
{
  "run_id": "20260913_153000_r7a1",
  "created_at": "2026-09-13T15:30:00+08:00",
  "manifest_version": "1.0",
  "adapter": "genshin",
  "adapter_version": "1.0",
  "project_commit": "c01e0a0",
  "project_dirty": true,
  "project_changed_files": ["app/retrieval.py"],
  "kb_manifest_hash": "kb_vectors_m3@2026-09-10",
  "evalset_file": "evalset/genshin/cases.json",
  "evalset_sha256": "…",
  "case_count": 26,
  "judge_model": "deepseek-chat",
  "judge_params": {"temperature": 0, "max_tokens": 512, "thinking": "disabled"},
  "judge_window": {"contexts_chars": 60000, "answer_chars": 20000, "reference_chars": 20000},
  "scorer_version": "1.0",
  "config_file": "evaluator/config.yaml",
  "config_sha256": "…",
  "status_per_case": {"R7": "ok"},
  "notes": ""
}
```

规则：

- manifest 在跑测开始时就写初版，跑完补 `status_per_case`；
- 中途被 kill 也要留下已写部分；
- 没有 `project_commit` / `kb_manifest_hash` / `evalset_sha256` 的 run 不能当基线。

## 四、判分口径

1. **判分窗口**
   - 进 config，不硬编码；默认 `contexts 60000 / answer 20000 / reference 20000`；
   - 窗口值写进 manifest；换窗口必须重算/重跑，不能直接与旧数比。
2. **Judge 模型**
   - 非推理模型；显式关闭 thinking；`temperature=0`；
   - 无 seed 的模型同题跑 2 次取中位，两次结果都落盘。
3. **空 content**
   - 必须显式报错：`ERROR:empty content (finish_reason=...)`；
   - 调用方标记 `judge_valid=false`，不得静默返回 `-1` 当有效分。
4. **计时**
   - `init_seconds` 与 `agent_seconds` 分开；评分耗时进 `scoring_seconds`；
   - 历史 `elapsed` 只作参考，不做跨轮趋势。
5. **噪声带**
   - 软指标（RAGAS 四维）只做同口径趋势；
   - 硬指标（must_contain / must_not_contain / 引用 / 工具数 / 超时）才做 pass/fail；
   - 同题重跑 2–3 次量出噪声带，带宽内的差异不算回归。
6. **缓存**
   - judge 缓存 key = `题面 hash + answer hash + contexts hash + judge_model + judge_params + judge_window + scorer_version`；
   - `rescore` 是一级命令：只换判分口径时复用已存 answer/contexts，不重跑被测 Agent。

## 五、题集 schema

保留现有字段，增加：

- `schema_version`
- `metadata.project` / `metadata.total_questions` / `metadata.kb_requirement`
- 每题：`tags`、`kb_requirement`、`visibility`（public/internal）
- 关键词对象化：

```json
{"text": "引蝶之章", "match": "literal"},
{"text": "扮演", "match": "semantic"},
{"text": "第三章", "match": "structural", "aliases": ["3.3 第三章"]}
```

三类含义：

- `literal`：专名/书名/角色名/核心设定术语，必须精确命中；
- `semantic`：判断语/态度词，允许 LLM 语义兜底；
- `structural`：任务名、编号、章节项，允许别名与结构匹配。

题集体检（`python -m evaluator.lint --cases … --results …`）检查：

- `metadata.total_questions` 与实际题数一致；
- 题面是否还在用已重命名的旧词；
- 关键词是否符合三类格式；
- 每个 `must_contain` 在历史 answer/contexts 里的命中数，长期 0 命中的提示复核。

## 六、迁移顺序

1. **Phase 1（当前）**：契约 + manifest + schema + lint + config 模板；
2. **Phase 2**：把 `tools/run_golden_test.py` 的子进程/超时/落盘抽成 `evaluator/harness.py`，评分抽成 `evaluator/scorers/`；
3. **Phase 3**：题集迁入 `evalset/<project>/cases.json`，跑一次 lint，C1/X2/R7 这类题集问题在 lint 阶段拦住；
4. **Phase 4**：医生项目写第二个 adapter，共用同一套 harness 和报告。

## 七、分工

- evaluator：题集 schema、lint、harness、scorers、manifest、报告、基线；
- 被测项目：adapter + 版本戳，不往 evaluator 塞项目逻辑；
- 医生项目：实现一次 adapter 即可接入，不需要重写评测。
